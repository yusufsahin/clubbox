# Windows 11 Smart App Control — Clubbox distribution

**Goal:** Ship Clubbox so Windows 11 Smart App Control (SAC) can trust it. Disabling SAC on the user’s machine is not the product answer.

Official references (Microsoft Learn):

- [Smart App Control overview](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview)
- [Sign your app for Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/code-signing-for-smart-app-control)
- [Test App Signatures with Smart App Control](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/test-your-app-with-smart-app-control)
- [Artifact Signing (formerly Trusted Signing) — Public Trust](https://learn.microsoft.com/en-us/azure/artifact-signing/concept-trust-models)

## What SAC actually checks

SAC allows a binary to run when **either**:

1. Microsoft’s app intelligence / Intelligent Security Graph predicts it is safe, **or**
2. It is signed with a certificate issued by a CA in the **Microsoft Trusted Root Program**.

For a personal / low-volume unofficial app, cloud reputation is unreliable (new hashes, few downloads). **Trusted Authenticode signatures on every PE that Clubbox launches are the reliable path.**

SAC evaluates binaries as they load — not only the outer installer. A signed setup that unpacks an unsigned `Clubbox.exe` (or other PE) can still fail at first run. Cover:

| Artifact | Why |
| --- | --- |
| NSIS setup (`Clubbox-*-setup.exe`) | User downloads and runs this |
| Portable (`Clubbox-*-portable.exe`) | Alternate distribution |
| App EXE (`win-unpacked/Clubbox.exe`) | Main process |
| Uninstaller (NSIS) | Generated by the installer |
| Any custom native `.exe` / `.dll` / `.node` we ship | Loaded at runtime |
| Electron / Chromium PE files left unsigned after we rewrite them | Must stay validly signed after packaging |

Electron’s own shipped DLLs usually keep the Electron publisher signature until modified. Our packaging must **re-sign** anything we produce or alter (`Clubbox.exe`, installers, elevators, etc.). Prefer **SHA-256** Authenticode + **RFC 3161 timestamp** so the signature remains valid after the signing cert expires.

Prefer **RSA** code-signing certificates. Microsoft’s SAC / Trusted Root guidance has historically rejected ECC/ECDSA for this path; do not rely on ECC even if some Learn pages mention it.

## Chosen path for this project (updated 2026-10-13)

**Primary for other users: Microsoft Store AppX** — see [`microsoft-store.md`](./microsoft-store.md). The Store re-signs the package; no paid Authenticode certificate required for Store installs.

**Fallback (NSIS/portable outside the Store): SSL.com IV + eSigner** (or Azure Artifact Signing if eligible).

Reasons:

- Azure Artifact Signing **Public Trust** is not available to individual publishers in Turkey (individuals: US/Canada only; org list also excludes TR).
- CA/B Forum rules require code-signing private keys in hardware or a cloud HSM — a downloadable `.pfx` is no longer the normal path for new IV/OV certs.
- eSigner lets electron-builder sign from this Windows machine without a USB token once the cert is enrolled.

### Owner-only step (cannot be done by the agent)

1. Order **IV Code Signing** at [SSL.com IV Code Signing](https://www.ssl.com/products/software-integrity/code-signing/iv/) (~$129/yr as of 2026).
2. Complete identity validation (government ID) — SSL.com emails a link.
3. Enroll the certificate in **eSigner** (cloud signing). Keep Tier 1 (~240 signs/yr) unless releasing often.
4. In the SSL.com dashboard, create an **eSigner API credential** (Client ID + Client Secret) and note the credential ID / username used for CodeSignTool.
5. Put secrets in a **gitignored** local file (see below) and tell the agent “sertifika hazır” — then `npm run dist:signed` + `npm run dist:verify` can finish SAC packaging.

Do **not** ask users to turn Smart App Control off.

### Alternate (only if eligible later)

Azure Artifact Signing Public Trust remains documented in older drafts for US/CA individuals or supported orgs. Not the Clubbox path today. `electron-builder.azure.example.json` stays for that rare case.

Never commit `.pfx`, eSigner secrets, or Azure client secrets.

## Build commands

| Command | Intent |
| --- | --- |
| `npm run dist` | Local / personal unpackaged installers — **unsigned** (`CSC_IDENTITY_AUTO_DISCOVERY=false`). Fine for the owner’s own machine; not SAC-ready for others. |
| `npm run dist:signed` | Release path — **fails** unless signing credentials are present; forces code signing. |
| `npm run dist:verify` | After a signed build: Assert Authenticode on setup, portable, and `win-unpacked` PE files we care about. |

Artifacts land in `../clubdeck-app/release/` (see `package.json` → `build.directories.output`).

### PFX / store signing (`dist:signed`)

```powershell
$env:WIN_CSC_LINK = "C:\path\to\codesign.pfx"   # or base64 of the file
$env:WIN_CSC_KEY_PASSWORD = "..."
npm run dist:signed
npm run dist:verify
```

### Azure Artifact Signing (`dist:signed`)

1. Copy `electron-builder.azure.example.json` → `electron-builder.azure.json` (gitignored).
2. Set Entra env vars (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`).
3. `npm run dist:signed` (the script detects `electron-builder.azure.json` and merges it).

## Pre-release checklist

1. `npm test` && `npx tsc --noEmit` && `npm run lint` && `npm run build`
2. `npm run dist:signed` on a clean tree with release credentials only
3. `npm run dist:verify` — every listed PE must be `Valid` / trusted publisher
4. On a **Windows 11 SAC evaluation** machine (or audit policy without ISG — see Microsoft “Test your app with Smart App Control”):
   - Install via NSIS setup
   - Launch Clubbox; open sandbox + one signed-in path the owner uses
   - Run portable once
   - Uninstall
   - Inspect **Event Viewer → Applications and Services Logs → Microsoft → Windows → CodeIntegrity → Operational** for 3076 (evaluation) / 3077 (enforcement) against Clubbox paths
5. Distribute only the signed setup/portable hashes you verified; do not re-zip `win-unpacked` without re-signing

## Free personal workaround (this machine, no cert)

Observed on the owner PC (2026-10-13): SAC policy state **On** (`VerifiedAndReputablePolicyState = 1`).

| Launch | Result |
| --- | --- |
| `../clubdeck-app/release/win-unpacked/Clubbox.exe` | **Blocked** — “Application Control policy has blocked this file” |
| `Clubbox-*-setup.exe` / portable | Same class of block (unsigned + unknown) |
| `node_modules/electron/dist/electron.exe` → `npm run desktop:preview` | **Runs** (Electron binary known to Microsoft app intelligence even when Authenticode shows NotSigned) |

So **you can use Clubbox without buying a certificate and without turning SAC off** by not installing the packaged EXE:

1. In the repo: double-click `Clubbox-dev.cmd`, or run `npm run desktop` / `npm run desktop:preview`.
2. Optional: pin that `.cmd` or a shortcut to the Start menu / taskbar.

This is **not** a distribution fix. Anyone else on a SAC-On PC still cannot run `Clubbox.exe` until you ship trusted signatures (paid) or they also run from source the same way.

clubdeck.app (TenPercent) currently ships Windows **NotSigned** too and asks users to crowdfund certificate renewal — same paid model, not a free SAC bypass.

## Out of scope / non-goals

- Telling users to turn SAC **Off** as the product answer (personal temporary Off remains their choice in Windows Security)
- Self-signed or private-CA certificates (not in Microsoft Trusted Root Program)
- Relying on SmartScreen reputation alone for a new publisher’s `Clubbox.exe`
- Automating Clubhouse or bypassing platform device checks (unchanged Clubbox hard rules)
